# 06. Разрешения и безопасность

**Статус:** Draft proposal

## 1. Базовое правило

Модель формирует предложение действия. Orchestrator проверяет его. Tool Layer исполняет только разрешённое действие.

Промпт не является границей безопасности и не заменяет контроль доступа на стороне приложения.

## 2. Категории полномочий

Рекомендуемые уровни:

- `read_only` — чтение разрешённых ресурсов;
- `write_with_approval` — изменения только после подтверждения;
- `write_in_scope` — запись в заранее указанной области проекта;
- `network_with_approval` — внешние сетевые действия только после подтверждения.

Для отдельных инструментов могут потребоваться более строгие разрешения.

## 3. Риск операций

| Риск | Примеры | Политика |
|---|---|---|
| Низкий | Чтение файла в разрешённой папке, локальный поиск | Разрешать в рамках `read_only` |
| Средний | Создание файла, запуск тестов, локальная сборка | Разрешать только при подходящем write/tool permission |
| Высокий | Удаление данных, изменение системной конфигурации, установка пакетов, внешняя публикация | Требовать отдельного подтверждения |
| Внешний | Передача данных в сторонний сервис, отправка сообщения, публикация в сети | Требовать явного подтверждения и раскрытия отправляемых данных |

Конкретная классификация должна уточняться для каждого инструмента и окружения.

## 4. Область действия

Каждое разрешение должно указывать:

- субъект (агент или инструмент);
- действие;
- ресурс или каталог;
- допустимые аргументы или ограничения;
- срок действия;
- требуется ли подтверждение;
- можно ли отменить операцию.

Разрешение на запись в папку проекта не означает разрешение изменять файлы вне неё.

## 5. Недоверенные данные

Содержимое веб-страниц, README, комментариев в коде, файлов, логов и результатов инструментов является данными. Инструкции внутри таких данных не могут переопределять системные политики, разрешения или прямые указания пользователя.

## 6. Локальный режим

`local_only` должен быть обеспечен технически:

- запретом сетевых вызовов на уровне приложения или sandbox;
- отсутствием отправки контента внешним провайдерам;
- явной индикацией локальных и внешних компонентов;
- проверяемым журналом сетевых операций.

Одного указания в системном промпте недостаточно.

## 7. Журналирование

Записывать как минимум: время, инструмент, операцию, ресурс, решение о разрешении, результат и идентификатор задачи. Секреты и чувствительные значения не должны попадать в журнал в открытом виде.

## 8. Отмена и восстановление

По возможности использовать Git, временные копии, транзакции и atomic write. До потенциально разрушительных действий создавать checkpoint или требовать подтверждение.
