# 02. Логическая архитектура

**Статус:** Draft proposal

## 1. Компоненты

### User Interface

Предоставляет доступ к проектам, задачам, артефактам, режимам помощи, разрешениям и журналу действий. UI не должен быть единственным местом хранения значимых данных.

### Orchestrator

Центральный контроллер процесса. Получает запрос пользователя, загружает состояние проекта, формирует контекст модели, проверяет предлагаемые операции, маршрутизирует вызовы и управляет переходами состояния.

Orchestrator должен реализовывать детерминированные проверки: разрешения, лимиты учебных инициатив, область задачи, допустимые переходы состояний и требования к подтверждению.

### Agent Core

Модель или набор моделей, выполняющие анализ, планирование, генерацию и интерпретацию результатов. Agent Core предлагает действия, но не обладает прямым обходным доступом к инструментам.

### Project Memory

Хранит проектный бриф, решения, источники, гипотезы, состояние и checkpoints. Извлечение контекста должно быть релевантным текущей задаче.

### Tool Layer

Единый интерфейс инструментов: файловая система, Git, терминал, тесты, браузер, приложения и внешние API. Каждый инструмент объявляет схему, риск и требования к разрешению.

### Verification

Запускает тесты, линтеры, статические анализаторы, проверки схем, сопоставление с источниками и другие подходящие способы подтверждения.

### Workspace

Файловое пространство пользователя. Содержит исходники, документы, результаты экспериментов и экспортируемые артефакты.

## 2. Поток запроса

1. UI отправляет запрос и идентификатор проекта.
2. Orchestrator загружает краткое состояние проекта и релевантные записи памяти.
3. Определяется активная задача или создаётся новая.
4. Политики выполнения и разрешения добавляются в контекст.
5. Agent Core предлагает ответ, план или действие.
6. Orchestrator проверяет действие по схеме и полномочиям.
7. Tool Layer выполняет разрешённую операцию.
8. Verification проверяет наблюдаемый результат.
9. Агент формирует отчёт, а система предлагает сохранить значимое решение или checkpoint.
10. Подтверждённые изменения проектной памяти фиксируются отдельно от сырого лога.

## 3. Граница доверия

Модель не должна иметь прямого доступа к секретам, произвольной сети или файловой системе в обход Tool Layer. Внешние документы, веб-страницы, репозитории, вывод терминала и содержимое файлов считаются недоверенными данными. Они не могут переопределить системные политики и разрешения.

## 4. Контракты между компонентами

Минимально следует определить:

- `TaskRequest` — запрос, цель, ограничения, режим и критерии;
- `ProposedAction` — инструмент, аргументы, область воздействия, обоснование;
- `PermissionDecision` — разрешено, запрещено или требуется подтверждение;
- `ToolResult` — результат, изменённые ресурсы, stdout/stderr, код возврата;
- `VerificationReport` — проверки и их результаты;
- `MemoryUpdateProposal` — предлагаемая запись памяти;
- `Checkpoint` — версия состояния проекта.

## 5. Состояния задачи

Рекомендуемый минимум:

`draft → ready → running → verifying → completed`

Дополнительные состояния: `blocked`, `cancelled`, `failed`, `needs_approval`.

Переходы должны быть явными. Например, `completed` нельзя присвоить при неуспешных обязательных критериях приёмки.

## 6. Технологическая нейтральность

На этапе концепции не следует привязывать архитектуру к конкретной модели, векторной базе, агентному фреймворку или UI. Сначала определить интерфейсы и требования, затем сравнить реализации.
