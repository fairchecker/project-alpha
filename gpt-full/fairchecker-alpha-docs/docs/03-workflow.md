# 03. Рабочий процесс

**Статус:** Draft proposal

## 1. Жизненный цикл проекта

### Инициализация

Пользователь задаёт общую цель, область проекта, ограничения и желаемый результат. Система формирует редактируемый `project brief`. Неизвестные поля можно оставить пустыми.

### Ориентация

Для новой задачи агент определяет контекст, известные факты, неизвестные, зависимости и возможные риски. Не следует превращать ориентацию в длинное интервью: вопрос задаётся, только если ответ существенно меняет следующий шаг.

### Планирование

Формируется план со следующими элементами:

- цель и ожидаемый артефакт;
- критерии приёмки;
- шаги и зависимости;
- риски и неизвестные;
- необходимые инструменты;
- операции, требующие подтверждения.

### Выполнение

Агент выполняет согласованные шаги в разрешённой области. По мере работы сохраняются существенные результаты и ссылки на артефакты.

### Проверка

Результат сопоставляется с критериями приёмки. Для кода это могут быть сборка, тесты, линтеры и ручная проверка. Для исследования — качество источников, воспроизводимость и согласованность выводов.

### Фиксация

Значимые решения, проверенные результаты и новые ограничения предлагаются к сохранению. Не следует сохранять каждую реплику в долговременную память.

### Передача и возобновление

Формируется краткий checkpoint, позволяющий продолжить работу в другой сессии, другим агентом или без Alpha.

## 2. Цикл задачи

`ориентация → план → выполнение → проверка → фиксация → продолжение/завершение`

Цикл не является строго линейным. Неуспешная проверка может вернуть задачу к анализу, планированию или реализации. Существенное изменение требований может потребовать повторной ориентации.

## 3. Когда спрашивать пользователя

Запросить решение пользователя, если:

- отсутствующая информация меняет архитектуру или результат;
- действие выходит за пределы текущей области;
- действие требует нового разрешения;
- существует несколько вариантов с существенными и труднообратимыми последствиями;
- критерии приёмки конфликтуют.

Не спрашивать, если ответ можно безопасно получить чтением доступных материалов или выполнить действие уже имеющимся разрешением.

## 4. Делегирование

Перед делегированием согласовать область задачи, ожидаемый результат и критерии приёмки. Для ограниченных и обратимых действий достаточно заранее предоставленного разрешения. Для разрушительных, внешних или труднообратимых операций требуется отдельное подтверждение.

## 5. Завершение

Задача может быть:

- `completed` — все обязательные критерии приёмки выполнены;
- `completed_with_limits` — результат получен, но некоторые проверки недоступны;
- `blocked` — продолжение невозможно без внешнего условия или решения;
- `failed` — попытка завершилась неуспешно;
- `cancelled` — работа остановлена пользователем.

Эти статусы нельзя смешивать.
