# 07. Память проекта и артефакты

**Статус:** Draft proposal

## 1. Цель памяти

Память должна позволять продолжить проект без повторного чтения всей переписки. Она хранит актуальное состояние и обоснованные записи, а не пытается сделать каждый токен диалога вечной памятью.

## 2. Слои памяти

1. **Project brief** — цель, область, ограничения и предпочтения.
2. **Task state** — активная задача, план, критерии приёмки и статус.
3. **Decision log** — принятые решения и основания.
4. **Evidence and sources** — источники, наблюдения, тесты и результаты.
5. **Hypotheses** — предположения, которые ещё предстоит проверить.
6. **Checkpoint** — состояние на момент остановки.
7. **Raw event log** — техническая история операций, отделённая от смысловой памяти.

## 3. Рекомендуемая структура

```text
project/
├── project.yaml
├── memory/
│   ├── decisions.md
│   ├── sources.md
│   ├── hypotheses.md
│   └── state.md
├── tasks/
│   ├── task-001.yaml
│   └── task-002.yaml
├── artifacts/
│   ├── documents/
│   ├── code/
│   └── experiments/
├── logs/
│   └── events.jsonl
└── export.md
```

Это предлагаемая структура, а не обязательная схема реализации. Для MVP можно начать с меньшего числа файлов.

## 4. Правила сохранения

- Значимое решение сначала предлагается к сохранению, если автоматическое сохранение явно не включено пользователем.
- Исторические решения не переписываются незаметно; новые сведения добавляются как пересмотр или superseding decision.
- Источник должен быть связан с утверждением, которое он поддерживает.
- Гипотеза не должна автоматически становиться фактом после повторения в нескольких сессиях.
- Сырой журнал и редактируемая память должны быть разделены.

## 5. Поиск контекста

При старте задачи загружать краткий бриф, активную задачу, последние checkpoints и релевантные решения. Не передавать модели весь архив автоматически: это увеличивает стоимость и создаёт шум.

## 6. Версионирование

Для файловых проектов предпочтительно использовать Git или эквивалентный механизм. Записи решений и схемы должны иметь дату и, при необходимости, идентификатор. Изменения памяти должны быть обозримыми и откатываемыми.

## 7. Экспорт

Пользователь должен иметь возможность экспортировать проект в обычные файлы Markdown, YAML, JSON и исходные артефакты без proprietary lock-in.
