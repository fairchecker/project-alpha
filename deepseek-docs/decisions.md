# Конкретные решения

Здесь то, что можно реализовать без догадок: форматы, состояния, порядок
сборки контекста и правила переходов. Всё — версия 0; менять по результатам
сессий.

## 1. Минимальная модель проекта

Один проект — одна папка:

```
project/
  brief.yaml        # цель, обучение, ограничения, режим
  decisions.md      # рабочие записи решений (дописываются)
  sources.md        # источники и что из них взято
  session.log.jsonl # сообщения, режимы, действия (не для чтения целиком)
  export.md         # генерируется командой export
```

`session.log.jsonl` — технический лог, не основной артефакт. `brief.yaml` и
`decisions.md` — то, что пользователь редактирует руками.

## 2. Схема брифа

```yaml
project: "Короткое имя"
question: "Что исследуем или строим, одним предложением"
artifact_goal: "Что должно появиться на выходе"
learning_goal: "Что пользователь хочет уметь или понимать"  # может быть null
mode: collaborate            # question | hint | collaborate | demonstrate | delegate
learning_budget: "medium"    # none | low | medium; high — только эксперимент, не MVP
constraints: []
privacy: "local-only"        # local-only | provider-ok
next_step: "Один следующий шаг"
```

Правила:

- Все поля, кроме `project` и `question`, необязательны при создании; `null`
  означает «не задано», а не «нет цели».
- `privacy` — жёсткое ограничение, а не пожелание: при `local-only` внешние
  вызовы моделей запрещены, инструмент деградирует в шаблоны и заметки.
- `learning_budget` управляет только частотой учебных вставок, не режимом.

## 3. Машина режимов

Состояние режима — в проекте, не в промпте. Режим меняется:

| Событие | Результат |
| --- | --- |
| Явная фраза («дай ответ», «режим подсказка», «просто сделай») | немедленная смена, без подтверждения |
| Кнопка/команда в интерфейсе | немедленная смена |
| Модель предлагает сменить режим | предложение в конце ответа, один раз |
| Пользователь молчит, режим не работает | модель продолжает текущий режим, не меняет сама |

Запрещено:

- менять режим внутри ответа без явного запроса;
- возвращаться к отклонённой учебной вставке в той же задаче;
- спрашивать «какой режим вам нужен?» чаще одного раза за сессию.

## 4. Бюджет обучения

`learning_budget` — это лимит, а не приглашение:

| Значение | Разрешено за сессию |
| --- | --- |
| none | 0 учебных вставок; только ответы, записи и пометки «не проверено» |
| low | 1 формат из `prediction`, `decision_replay`, `contrast_pair` |
| medium | до 3; плюс `error_autopsy`, `source_audit`, `explain_back` |
| high *(эксперимент, не MVP)* | до 5; плюс `worked_example` |

`handoff` (следующий шаг в конце сессии) разрешён всегда, потому что это не
учебная вставка, а закрытие сессии.

Естественная пауза — завершённая подзадача, разрешённая ошибка, готовый
артефакт, явный вопрос пользователя, конец сессии. Не пауза — середина ответа и
любое место, где пользователь ещё не получил результат.

## 5. Формат записи решения

```md
## YYYY-MM-DD — <решение одним предложением>

- Почему: <причина, 1–2 строки>
- Альтернативы: <что рассматривали и почему отклонили>
- Не проверено: <что осталось без доказательства>
```

Ограничения:

- максимум 5 строк на решение (без заголовка);
- запись создаётся только по согласию пользователя или его правке;
- старые записи не переписываются; новое решение — новая запись;
- при экспорте записи идут в хронологическом порядке, без «умного» слияния.

## 6. Порядок сборки контекста

1. Системный промпт инструмента (режим, правила).
2. Бриф проекта (целиком — он мал по дизайну).
3. Последние 10–15 сообщений сессии.
4. Релевантные записи решений (по ключевым словам, не все).
5. Источники, если пользователь на них сослался.

Правило: если бриф не влезает в контекст — это ошибка дизайна брифа, а не повод
его сокращать моделью.

## 7. Экспорт

`export` собирает один `export.md`:

- бриф;
- хронологию решений;
- источники;
- открытые вопросы;
- последнюю рефлексию (если была).

Без чата целиком: чат — расходный материал, экспорт — рабочий документ.
Пользователь может запросить и полный лог отдельно.

## 8. Состояние обучения

Счётчики и флаг отказа хранятся в состоянии проекта, а не выводятся моделью из
истории. Модель получает только эти значения.

```json
{
  "learning_budget": "medium",
  "learning_offers": 2,
  "learning_accepted": 1,
  "formats_used": ["prediction"],
  "refusal_in_task": false
}
```

Правила:

- `learning_offers` увеличивается, когда формат предложен; `learning_accepted` —
  когда пользователь выполнил действие, а не просто согласился.
- `refusal_in_task` ставится при любой фразе отказа и снимается только в новой
  задаче, не в новой сессии. Новая задача — явная команда/кнопка, а не просто
  новое сообщение.
- Формат запрещён, если `refusal_in_task = true` или
  `learning_offers >= лимит(budget)`.
- `formats_used` нужен, чтобы не повторять один формат чаще двух раз подряд.
- Инструмент проверяет лимиты до вызова модели; модель не является последней
  инстанцией.

## 9. Сборка системного промпта

Порядок:

1. `system-prompt.md` — базовый контракт (режим, обучение, записи, запреты).
2. Блок состояния из п. 8 и `system-prompt.md`, п. 1.
3. Режимная вставка, если полный промпт не влезает.
4. Бриф проекта целиком.
5. Последние 10–15 сообщений сессии.
6. Релевантные записи решений (по ключевым словам, не все).
7. Источники, если пользователь на них сослался.

Правило: если блок состояния занимает больше ~1k токенов — это ошибка дизайна
состояния, а не повод сокращать его моделью. Если бриф не влезает — ошибка
брифа.

## 10. Приватность и удаление

- `local-only` блокирует внешние вызовы на уровне транспорта, а не просьбой в
  промпте. Проверяется тестом: при флаге ни один сетевой вызов не уходит.
- При `provider-ok` перед первым вызовом показывается, какие поля брифа и
  сообщений уйдут провайдеру.
- `alpha delete --project` удаляет папку проекта целиком, включая лог.
- `alpha export` работает офлайн и не требует модели.
- `session.log.jsonl` не попадает в экспорт по умолчанию; только по отдельному
  запросу.
- Никакой фоновой синхронизации и «памяти между проектами» в MVP.

## 11. План проверки MVP

Гипотезы и способ проверки на 3 проектах и 10+ сессиях:

| Гипотеза | Как проверяем | Провал, если |
| --- | --- | --- |
| Режимы используются осознанно | лог смен режимов | >80% сессий без смены и без явного выбора при старте |
| Записи решений полезны | повторное открытие через неделю | никто не открывает и не редактирует `decisions.md` |
| Форматы обучения не раздражают | лог: предложено / принято / выполнено | принято <30% или выполнено <50% |
| Обучение не мешает | жалобы и отказы | отказ от форматов в >30% случаев, или раздражение в интервью |
| «Продолжи без модели» работает | вопрос в конце сессии | пользователь не может назвать следующий шаг в большинстве сессий |
| Приватность не блокирует | число проектов с `local-only` | режим `local-only` делает инструмент бесполезным |

Минимум для вывода: 10 сессий, 3 проекта, 3 пользователя, включая хотя бы одну
провальную сессию. Оценки модели о «понял/не понял» в расчёт не берутся.
